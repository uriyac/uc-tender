# UX-FLOWS.md — מסעות משתמש

> פורמט: Actor → Action → System Response → Outcome
> לא עיצוב — לוגיקה בלבד.

---

## Flow 1: Onboarding — "חינוך המערכת"

**פרסונה:** יוסי (VP BizDev)
**טריגר:** כניסה ראשונה למערכת
**מטרה:** Knowledge Base מאוכלס ומוכן לעבודה

```
יוסי נכנס למערכת לראשונה
  → מערכת: מציגה Welcome Screen עם 3 שלבים ברורים
  
יוסי בוחר: "התחל העלאת מסמכים"
  → מערכת: פותחת ממשק העלאה (drag & drop)
  
יוסי מעלה כל מה שיש לו: קורות חיים, אישורים, פרויקטים, מאזנים
  → מערכת: קולטת, מעבדת, מציגה progress bar
  → מערכת: "זיהינו 12 פרויקטים, 3 אישורים, 2 מסמכים פיננסיים"
  
יוסי סוקר את מה שהמערכת זיהתה
  → מערכת: מציגה כרטיסיות לכל פרויקט עם הממדים שחילצה
  → יוסי יכול לאשר / לתקן / להוסיף
  
✅ Knowledge Base פעיל — יוסי מוכן לראשון מכרז
```

**נקודות כאב UX לפתור:**
- העלאה צריכה לתמוך בכמה עשרות קבצים בבת אחת
- המשתמש צריך לראות "מה המערכת למדה" — לא רק "הועלה"
- חייב להיות ניתן לחזור ולהשלים מאוחר יותר (Save-State)

## Flow 2: Tender Intake — "הזנת מכרז חדש"

**פרסונה:** יוסי
**טריגר:** יוסי קיבל מכרז שרלוונטי לחברה
**מטרה:** Go/No-Go decision מבוסס נתונים

```
יוסי לוחץ "New Tender"
  → מערכת: שואלת כיצד להזין (העלאת PDF / הדבקת טקסט)
  
יוסי מעלה מסמך המכרז
  → מערכת: מפענחת תנאי סף, דרישות, deadline
  → מערכת: מצליבה מול Knowledge Base
  
מערכת מציגה:
  - Match Score: 78%
  - ✅ עומדים ב: ניסיון רב-שנתי, אישור ISO, ניסיון ב-3+ רשויות
  - ⚠️ פערים: חסר אישור ניכוי מס בתוקף, חסר ניסיון ספציפי בתחום X
  - ⏰ Deadline: 14 ימים

יוסי מחליט: Go
  → לוחץ "המשך לטיוטה"
  
יוסי מחליט: No-Go
  → לוחץ "ארכב" — המכרז נשמר לניתוח עתידי
```

**נקודות כאב UX לפתור:**
- Gap Analysis צריך להיות ברמת "מה צריך לעשות" — לא רק "מה חסר"
- Match Score צריך הסבר — לא מספר קסם

## Flow 3: Draft Generation — "גמישות מכרזית"

**פרסונה:** יוסי (מאשר) / מיכל (מבצעת — Phase 2)
**טריגר:** החלטת Go
**מטרה:** טיוטת הגשה מוכנה לעריכה סופית

```
יוסי לוחץ "צור טיוטה"
  → מערכת: מציגה mapping — "אלו הפרויקטים שאני מתכוונת להשתמש בהם"
  
מערכת מציגה לדוגמה:
  - "פרויקט קשרי קהילה → נשתמש בממד הסקרים וניתוח הנתונים שלו"
  - "פרויקט תשתיות → נשתמש בממד הניהול הרב-רשותי שלו"
  
יוסי יכול: לאשר / לשנות את ה-mapping / להחריג פרויקט
  → לוחץ "צור"
  
מערכת מייצרת טיוטה:
  - פרקי איכות ההצעה
  - ניסיון מציע — מנוסח בשפת המכרז
  - כל טענה עם הפניה למקור בזיכרון הארגוני
  
יוסי רואה טיוטה + כפתור "הורד Word"
  
⚠️ אם נתון חסר: המערכת מסמנת בצהוב "נדרש השלמה ידנית"
  ← לא ממציאה. מדגישה את החסר.
```

## Flow 4: Post-Submission Learning — "המערכת לומדת"

**פרסונה:** יוסי / מיכל
**טריגר:** לאחר הגשת מכרז בפועל
**מטרה:** Knowledge Base גדל

```
לאחר הגשה: יוסי מעלה את מה שנגיש בפועל
  → מערכת: "תודה. למדתי X נתונים חדשים לזיכרון הארגוני"
  → מערכת: מעדכנת את הפרופיל של הפרויקטים שנעשה בהם שימוש

לאחר תוצאה (זכייה / פסילה): יוסי מדווח
  → מערכת: מסמנת מה עבד / מה לשפר בפעם הבאה
```

## Happy Path — הכל בפרספקטיבה

```
[יום 1]  Onboarding — העלאת מסמכים
[יום 2]  Tender Intake — מכרז ראשון נכנס
[יום 2]  Go/No-Go — ציון 78%, מחליטים Go
[יום 3]  Draft Generation — טיוטה ראשונה מוכנה
[יום 3]  עריכה ידנית סופית על ידי הצוות
[יום 5]  הגשה
[יום 6]  Post-Submission Upload — המערכת לומדת
```
