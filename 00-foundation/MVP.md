## הגדרת MVP

MVP הושלם כאשר: **חברה יכולה להעלות את המסמכים שלה, להזין מכרז חדש, ולקבל טיוטת הגשה מותאמת — בלי להמציא שום דבר שלא כבר קיים בזיכרון החברה.**

---

## מה בפנים ✅

### מודול א' — זיכרון ארגוני (Knowledge Base)
- העלאת מסמכים (PDF, Word, Excel) של החברה
- עיבוד אוטומטי → פירוק לעובדות מובנות (ממדים)
- ממשק צפייה + עריכה של מה שהמערכת למדה
- שמירה ולמידה מכל מכרז שנגיש בעבר

### מודול ב' — קליטת מכרז (Tender Intake)
- הזנת מכרז חדש (העלאת מסמך)
- פענוח אוטומטי של תנאי סף ודרישות
- הצגת Gap Analysis: "עומדים ב-X, חסר Y"
- ציון התאמה (Match Score)

### מודול ג' — חולל הטיוטה (Draft Generator)
- יצירת טיוטה המבוססת על ממדים מהזיכרון הארגוני בלבד
- גמישות מכרזית: אותו פרויקט — הדגשה שונה לפי דרישת המכרז
- הורדת טיוטה לעריכה (Word / PDF)
- **אין הזיות**: אם הנתון לא קיים בזיכרון — המערכת מדגישה זאת, לא ממציאה

## מה בחוץ ❌

| Feature | למה לא עכשיו |
|---------|--------------|
| Tender Radar / סריקת מכרזים חדשים | מורכבות תחזוקה גבוהה, לא ה-core value |
| הגשה אוטומטית לפורטלים ממשלתיים | חוסר סטנדרטיזציה — בור ללא תחתית |

| ניהול פרויקטים אחרי זכייה | מחוץ לתחום — המוצר מסתיים בהגשה |
| אינטגרציה ל-API ממשלתי (מבז"ק, 1000) | Phase 2 |

## מסע המשתמש ב-MVP (end-to-end)

```
1. ONBOARDING
   חברה מעלה מסמכים →
   המערכת לומדת ומארגנת →
   Knowledge Base מוכן

2. TENDER INTAKE
   המשתמש מעלה מכרז חדש →
   המערכת מפענחת דרישות →
   מציגה Match Score + Gap Analysis

3. DRAFT GENERATION
   לחיצת כפתור →
   המערכת שולפת ממדים רלוונטיים מהזיכרון →
   מייצרת טיוטה →
   המשתמש מוריד ועורך

4. POST-SUBMISSION LEARNING
   המשתמש מעלה את מה שנגיש בפועל →
   המערכת לומדת →
   Knowledge Base גדל
```

## KPIs למדידת הצלחה

| מדד | יעד |
|-----|-----|
| Onboarding Completion Rate | מעל 70% מסיימים העלאת מסמכים ראשונית |
| Time-to-Draft | ירידה של 60%+ לעומת תהליך ידני |
| Zero Technical Disqualifications | 0% פסילות על פגמים שהמערכת סרקה |
| Edit Distance Score | פחות מ-20% עריכות עובדתיות על הטיוטה |
