# S4 — לולאת למידה — מסמך גישה ומחקר

> מטרה: לתכנן את לולאת הלמידה כ**moat אמיתי** — לא "עוד מערכת שלומדת", אלא כזו שנותנת
> יתרון מתחדד שמערכת רגילה לצידה לא יכולה לשחזר. נגזר מ-[EXECUTION-PLAN](EXECUTION-PLAN.md) S4.

---

## 1. המחקר — מה השוק כבר עושה (וממה להיזהר)

**Win/Loss analysis (שיטות מקובלות):**
- לקודד כל תוצאה ל**קטגוריות-סיבה קבועות** (לא טקסט חופשי), לתעד מיד "כשזה טרי".
- למדוד win-rate **לפי סוג מכרז**, לא רק כולל; ולנתח את **התפלגות סיבות ההפסד** כדי למצוא את הפער הגדול הניתן-לתיקון.
- לסקור אילו סעיפים/מסרים/תמחור חוזרים בהצעות שזכו.

**כלי RFP/AI (הכיוון של השוק):**
- ספריית-תוכן מרכזית שקולטת כל הצעה קודמת, עם semantic matching והמלצת תוכן.
- "flywheel": כל הגשה נכנסת אוטומטית למאגר; בחלק מהכלים 60–70% מהתשובה מתמלאת מהמאגר.
- bid/no-bid מבוסס היסטוריית פרויקטים.

**המסקנה החדה:** "ללמוד מהעבר" **כבר לא בידול** — כולם עושים תוכן-מצטבר. אם נעצור שם, אנחנו
"עוד כלי RFP". הבידול חייב להיות **איפה** ו**איך** לומדים.

---

## 2. הבידול שלנו — למה זה עדיף מכל מערכת רגילה לצידה

| ממד | מערכת רגילה / כלי RFP | **UC TENDER** |
|-----|----------------------|----------------|
| מה נלמד | ספריית-תוכן: "מה כתבנו" | **פלייווהיל מכויל-תוצאה**: "מה זכה/הפסיד ו**למה**" |
| אמון בנלמד | מייצר תוכן, נוטה להזיות | **אפס-הזיות + ציטוט מקור על כל עובדה נלמדת** (audit trail) |
| פרופיל | סטטי (כמו bido) | **זיכרון מפרסם** — עיריית X שוקלת Y; סיבות פסילה אמיתיות שלה |
| ציון התאמה | "עיוור", לא נבדק מול מציאות | **כיול ניבוי** — חזינו Go/score, התוצאה מתקנת → הביטחון נעשה אמין |
| נראוּת | למידה בלתי-נראית ברקע | **למידה גלויה** — "המערכת למדה X מההגשה האחרונה" |

**שורת המוט:** מתחרה שמתחיל מחר יכול לבנות ספריית-תוכן. הוא **לא** יכול לשחזר את
היסטוריית התוצאות-והסיבות שלך מול מפרסמים ספציפיים, ואת הכיול שנצבר עליה. זה data-moat
שמתחדד עם כל הגשה — וככל שהלקוח משתמש יותר, יקר לו יותר לעזוב.

## 3. מה לוכדים — סכמת תוצאה מובנית (S4.1)

היום `submitOutcome` לוכד `result` + `reason` (טקסט חופשי) + קבצים. נשדרג ל:

```
outcome = {
  result: 'win' | 'lose' | 'pending',
  reason_code: <קטגוריה סגורה>,      // ← הליבה: קידוד, לא טקסט חופשי
  reason_note: string,               // חופשי, לצבע בלבד — לא נכנס כ"עובדה"
  final_rank / winner_price: ?,      // אם ידוע
  prediction: { match_score, go_decision, red_flags },  // ← ננעל בזמן ההגשה
  files: [...]                       // ההגשה בפועל → ראיות מנצחות
}
```

**קטגוריות-סיבה סגורות** (reason_code):
`מחיר` · `ניקוד טכני` · `חוסר מסמך/כשירות` · `אי-עמידה בתנאי סף` · `פסילה טכנית (פורמלית)` ·
`החלטת מזמין/שק"ד` · `ביטול המכרז` · `אחר`.
(רשימה סגורה = ניתן לצבור התפלגות ולמצוא את הפער הגדול; חופשי = רעש.)

## 4. חמשת אותות הלמידה — מה מפיקים מכל תוצאה

1. **זיכרון מפרסם** (issuer memory): אגרגציה לפי `issuer` → כמה הגשנו/זכינו, סיבות הפסד נפוצות,
   הטיות ("מפרסם זה פוסל על פורמליות" / "שוקל מחיר גבוה"). → באנר בהזנת מכרז מאותו מפרסם.
2. **כיול ניבוי** (calibration): לכל מכרז שנסגר — השוואת ה-prediction שננעל מול ה-outcome.
   מצטבר ל-calibration-error → **מתקן את סף ה-Go/No-Go ואת מספרי הביטחון** שיוצגו בעתיד.
3. **ראיות מנצחות** (winning evidence): מסמכי הגשה שזכו → `extractKnowledge` → מאגר ידע מסומן-מקור,
   זמין לטיוטות הבאות (תחת ה-guardrail). "פסקה שזכתה" עדיפה על פסקה גנרית.
4. **מפת פערים→תוצאה** (gap→outcome): אילו פערים שדגלנו עליהם באמת נכחו בהפסדים →
   **מחדד את דירוג הדגלים** (S1.1): דגל שגרם הפסד בעבר עולה לחומרה גבוהה.
5. **מציאות תנאי-סף** (threshold reality): reason_code של פסילה → מחדד `checkRedFlags`/`checkThresholds`
   (למשל: אם נפסלנו על ערבות פגה — הדגל "ערבות" יודגש חזק יותר במפרסם הזה).

---

## 5. איך זה מוזרם חזרה למנוע (Claude-ready)

הכל מאחורי חוזה המנוע — key-free עכשיו (heuristics + אגרגציות), Claude מעמיק בהמשך בלי שכתוב:

| פונקציית מנוע | ההזרמה מהלמידה |
|----------------|----------------|
| `analyzeMatch` / `buildMapping` | boosting מראיות מנצחות; רמזי מפרסם |
| `checkRedFlags` | דגלים שהתממשו בהפסדים → חומרה גבוהה יותר |
| `checkThresholds` | סיבות פסילה שנלמדו → הדגשה |
| confidence בטיוטה | מכויל מנתוני calibration (במקום מספר קבוע) |

**עיקרון:** הלמידה מוזרמת כ**קלט נוסף** לפונקציות הקיימות (context), לא כמסלול נפרד — כך ה-guardrail והחוזה נשמרים.

---

## 6. הלמידה הגלויה — ה-UX שהופך moat למוחשי (S4.6)

מתחרה "לומד ברקע". אנחנו **מראים** את זה:
- **"מה המערכת למדה"** — כרטיס/פיד: אחרי כל תוצאה, בדיוק מה השתנה (X נוסף למאגר, דגל Y התחדד).
- **באנר מפרסם** בהזנת מכרז: "כבר התמודדנו מול עיריית X — 3 הגשות, סיבת הפסד נפוצה: פורמליות."
- **מד ביטחון שמשתפר** — calibration לאורך זמן (הגרף שאומר "אני נעשה אמין").
- **מדד flywheel בדשבורד** — כמה ידע/ראיות/כיול נצברו.

---

## 7. אפס-הזיות על הלמידה — הגבול שאסור לחצות

- כל עובדה נלמדת נושאת **מקור** (איזו הגשה/תוצאה). ה-guardrail חל גם על ראיות מנצחות בטיוטה.
- **reason_code מרשימה סגורה** — טקסט חופשי (reason_note) הוא צבע בלבד, לעולם לא נכנס כ"עובדה" למאגר.
- **calibration = נתון מדיד** (predicted vs actual), לא דעה. מספר הביטחון מגובה בנתונים.
- למידה לא "ממציאה" הטיית-מפרסם מדגימה אחת — סף מינימלי של הגשות לפני שמפרסם-הטיה מוצג.

## 8. תוכנית יישום — S4 בתת-שלבים (key-free, Claude-ready, guardrail)

| # | תת-שלב | פלט |
|---|--------|-----|
| S4.1 | **סכמת תוצאה מובנית + reason_code** (הרחבת submitOutcome + נעילת prediction בהגשה) | לכידה איכותית |
| S4.2 | **זיכרון מפרסם** (אגרגציה לפי issuer) + באנר בהזנה | "כבר ראינו את X" |
| S4.3 | **כיול ניבוי** (prediction log → calibration-error) | ביטחון אמין |
| S4.4 | **ראיות מנצחות** (extractKnowledge מהגשות זוכות — קיים חלקית, לחזק+לסמן) | מאגר מנצח |
| S4.5 | **מפת פערים→תוצאה** → חידוד דירוג הדגלים | דגלים חכמים יותר |
| S4.6 | **למידה גלויה** (כרטיס "מה למדנו" + מד flywheel) | ה-moat מוחשי |

**סדר מומלץ:** S4.1 (הבסיס — בלי לכידה טובה אין למידה) → S4.2 + S4.6 (ערך נראה-לעין מהיר) →
S4.3 (כיול) → S4.4/S4.5 (העמקה).

---

## 9. מדדי הצלחה
- **calibration-error יורד לאורך זמן** (המדד המרכזי לכך שהלמידה עובדת).
- win-rate לפי סוג מכרז + התפלגות reason_code (הפער הגדול הניתן-לתיקון).
- % טיוטה מכוסה בראיות מנצחות.
- "זמן-עד-החלטת-Go" יורד ככל שזיכרון-המפרסם מתעשר.
